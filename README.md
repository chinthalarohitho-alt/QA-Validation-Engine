# QA Validation Engine

[![PR checks](https://github.com/OWNER/qa-validation-engine/actions/workflows/pr-checks.yml/badge.svg)](https://github.com/OWNER/qa-validation-engine/actions/workflows/pr-checks.yml)
[![Nightly regression](https://github.com/OWNER/qa-validation-engine/actions/workflows/nightly.yml/badge.svg)](https://github.com/OWNER/qa-validation-engine/actions/workflows/nightly.yml)

> One repository, one runner, three kinds of testing: **web UI**, **API contracts** and
> **load** — reported together in a single Allure 3 report, run on every pull request and every
> night in GitHub Actions.

It mirrors the architecture of a production framework I built for a multi-product healthcare
SaaS platform. This public version runs against three public demo systems instead, so anyone can
clone it and watch every lane pass:

| Product | Target | Lane | What it proves |
|---|---|---|---|
| `storefront` | [SauceDemo](https://www.saucedemo.com) | Web UI — Playwright + Gherkin | Login, catalogue, cart, and checkout money maths, per persona |
| `shop-api` | [DummyJSON](https://dummyjson.com) | API — Playwright + Gherkin, no browser | Contracts (JSON Schema), an auth guard matrix, pagination/search/sort, cart arithmetic |
| `pizza-service` | [QuickPizza](https://quickpizza.grafana.com) (Grafana's k6 demo) | Load — k6 | p95 budgets per endpoint, and correctness checks held *under load* |

**Current state:** 30 web scenarios, 35 API scenarios, 2 load scripts (21 thresholds and checks)
— 86 results in one report, plus 4 real defects in the targets, each pinned by a self-retiring
test (see [Known defects](knowledge-base/known-defects.md)).

## Highlights

- **Money is asserted in integer cents, re-derived from what the user saw.** The checkout tests
  record each price as it is added from the catalogue, then check subtotal, 8% tax and total
  separately — so the report names *which* rule broke. A mutation test (tax rate 8% → 7%) fails
  them on the exact cents.
- **Personas by tag.** `@as-problem-user` runs a scenario as a different account. Each persona
  signs in once per run in `globalSetup`; its saved session is reused only while the session
  cookie itself is still valid.
- **Self-retiring known defects.** A scenario tagged `@known-defect @fail` is *expected* to fail.
  The build stays green while the bug exists, and turns red the day it is fixed, so a known
  defect can't outlive its bug unnoticed.
- **An auth matrix, not one negative test.** Every protected route × no header / empty header /
  non-JWT / tampered JWT. Building it surfaced a real defect: a tampered signature answers
  **500** instead of 401.
- **Load tests that check answers, not only status codes.** Under load a service can stay fast
  by returning wrong results. The k6 scripts assert that each recommendation honours the
  vegetarian, exclusion and calorie constraints it was asked for.
- **k6 results in the same report.** A runner injects hosts from the one env config (k6 has no
  `process`), then turns each threshold and check into an Allure test.
- **Sharded CI with one merged report.** PR: typecheck → API + sharded web smoke + k6 smoke →
  Allure artifact. Nightly: full regression over 3 shards → Allure with history trends →
  GitHub Pages → optional Slack message.

## Architecture

```
projects/                          # WHAT is tested — feature files and k6 scripts, by product
  storefront/<module>/ui/{smoke,regression}/*.feature
  shop-api/<module>/api/{smoke,regression}/*.feature
  pizza-service/<module>/k6/*.ts
shared/                            # HOW it is tested — reused by every product
  config/        env.config.ts (one host table) · roles.config.ts (personas) · auth.setup.ts
  ui/            pages/ (page objects) · steps/ · fixtures/ (persona + page-object injection)
  api/           request.client.ts · schemas/ · payloads/ · steps/ · fixtures/
  k6/            profiles and thresholds (k6.config.ts) · k6-side env access (runtime.ts)
  factories/     test-data builders
  scripts/       run-k6.ts · k6-to-allure.ts
  money.helper.ts                  # cent-exact arithmetic shared by UI and API assertions
knowledge-base/                    # known defects, open questions, lessons learned
.github/                           # PR + nightly workflows, a composite setup action
```

The two Playwright lanes are generated by separate `defineBddConfig` calls. The API lane's
steps never ask for `page`, so Playwright never launches a browser for them.

## Run it

```bash
nvm use                       # Node version from .nvmrc
npm ci
npx playwright install chromium
brew install k6               # or see https://grafana.com/docs/k6/latest/set-up/install-k6/
```

No `.env` is needed: every credential defaults to the targets' published demo login.
`.env.example` shows where real secrets would go.

| Command | Runs |
|---|---|
| `npm test` | All web scenarios |
| `npm run test:smoke` / `test:regression` | Web, by tag |
| `npm run test:api` | All API scenarios (no browser) |
| `npm run k6:all` | Every k6 script, smoke profile |
| `npm run k6 -- <script> --profile load` | One k6 script, another profile |
| `npm run test:everything` | Clean, typecheck, all three lanes |
| `npm run allure:all` | Open the combined report |
| `npm run quality` | Typecheck (Node + k6) and BDD generation |

## Adding a test

1. Write the scenario in a `.feature` file under `projects/<product>/<module>/{ui|api}/{smoke|regression}/`.
2. Tag it `@smoke` or `@regression`, a module tag, and a unique id (`@web-cart-05`).
3. Reuse an existing step if one says what you mean; otherwise add one in `shared/{ui|api}/steps/`.
   `npm run quality` fails if any step is unimplemented.
